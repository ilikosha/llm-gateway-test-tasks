# Напоминания о периодических задачах (Django + Celery)

Небольшой сервис: у компаний есть периодические задачи с ответственным по email.
Ежедневно Celery beat запускает задачу, которая находит задачи со сроком в ближайшие
3 дня и отправляет каждому ответственному **одно** письмо-дайджест со всеми его задачами.

## Состав

- `reminders/models.py` — `Company`, `Task`, `DigestLog` (журнал отправок).
- `reminders/services.py` — выбор задач и отправка дайджестов (вся логика).
- `reminders/tasks.py` — celery-задача `reminders.send_due_digests`.
- `config/celery.py` — расписание beat: каждый день в 08:00 (Asia/Almaty).
- `reminders/admin.py` — админка, действие «Отметить выполненными (сегодня)».
- Команды: `send_digests` (отправить синхронно), `seed_demo` (демо-данные).

## Запуск в Docker

```bash
docker compose up -d --build        # web, db (PostgreSQL), redis, celery, beat
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py seed_demo    # демо-данные
```

Админка: http://localhost:8000/admin/. Письма выводятся в консоль (бэкенд
`console.EmailBackend`) — смотреть в `docker compose logs celery`.

Запустить дайджест вручную через воркер:

```bash
docker compose exec celery celery -A config call reminders.send_due_digests
docker compose logs celery | tail -30
```

Остановить и удалить данные: `docker compose down -v`.

## Локальный запуск (без Docker)

Нужен [uv](https://docs.astral.sh/uv/). Без `DATABASE_URL` используется SQLite.

```bash
uv sync
uv run python manage.py migrate
uv run python manage.py seed_demo
uv run python manage.py send_digests      # письма в консоль
```

## Страница «Ближайшие сроки» (HTMX)

`/upcoming/` — список активных задач со сроком в ближайшие N дней (3 / 7 / 30, по
умолчанию 3), включая просроченные (подсвечены красным) и ни разу не выполнявшиеся.
Сортировка по сроку; фильтр по компании. Переключение периода и компании идёт через
HTMX без перезагрузки страницы (запрос с заголовком `HX-Request` возвращает только
фрагмент списка; URL обновляется, ссылку можно сохранить). Кнопка «Выполнено» делает
HTMX POST на `/upcoming/<id>/done/` (CSRF-токен передаётся заголовком `X-CSRFToken`),
ставит `last_done_date = сегодня` и подменяет строку.

Доступ — для сотрудников (`is_staff`) через сессию админки: войдите на
`/admin/login/`, затем откройте `/upcoming/` (без входа будет редирект на логин админки).
HTMX подключается с CDN: `https://unpkg.com/htmx.org@2.0.4`.

## Тесты

```bash
uv run pytest
```

Тесты идут на SQLite, Docker не нужен. Покрыто: граничные случаи `Task.is_due`,
дайджест (одно письмо на ответственного, исключение не наступивших и приостановленных,
границы окна (сегодня, +3 дня включено, +4 исключено, просрочено), отсутствие дубля при повторном запуске, повтор после сбоя отправки) и действие
«выполнено» в админке, страница `/upcoming/` (полная страница и HTMX-фрагмент, фильтры, доступ, POST-only «Выполнено», CSRF).

## Проектные решения

- **`Task.is_due(days_ahead)`**: срок = `last_done_date + cycle_days`. Задача due, если
  срок `<= сегодня + days_ahead` (граница включительна).
  **Просроченные считаются due** — иначе о забытой задаче напоминание бы замолчало.
  **Ни разу не выполнявшаяся задача считается due** (срока нет, считаем, что он наступил).
- **Статус**: `Активна` / `Приостановлена`. Дайджест учитывает только активные задачи.
  «Выполнено» — это действие, а не статус: периодическая задача не «закрывается»,
  а просто сдвигает следующий срок.
- **Отметка «выполнено»**: действие в админке ставит `last_done_date = сегодня`
  (по `Asia/Almaty`), следующий срок пересчитывается автоматически. Дату можно
  также поправить вручную в форме задачи.
- **Идемпотентность**: `DigestLog` с уникальным ограничением `(email, sent_on)`.
  Запись создаётся в одной транзакции с отправкой: повторный или параллельный запуск
  упирается в уникальность и пропускает адрес; если отправка упала, запись
  откатывается и следующий запуск повторит попытку. Email сравниваются без учёта регистра.
- **Фильтрация сроков в Python**, а не в SQL: `is_due` — единственный источник правды
  о правилах, арифметика дат не зависит от СУБД. Для тысяч задач это незаметно;
  при росте на порядки логику можно перенести в SQL-аннотацию.
- **Настройки через окружение**: `DATABASE_URL`, `CELERY_BROKER_URL`, `EMAIL_BACKEND`,
  `DIGEST_DAYS_AHEAD` (по умолчанию 3), `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`.
  Для продакшена задайте свой секрет и `DJANGO_DEBUG=0`, а также SMTP-бэкенд.

## Известное ограничение

Письмо отправляется внутри транзакции, которая создаёт запись `DigestLog`. Если SMTP принял письмо, а фиксация транзакции после этого не удалась (обрыв соединения с БД), следующий запуск отправит дайджест повторно. Мы сознательно выбрали «не больше одного лишнего письма» вместо «риска не отправить вовсе». Для гарантии ровно одной доставки нужна очередь исходящих писем (outbox) с отдельным отправщиком, это следующий шаг при переходе на реальный SMTP.
