# Rate-limited echo (sliding window)

FastAPI-сервис с эндпоинтом `POST /v1/echo`, который возвращает тело JSON-запроса как есть.
Для каждого API-ключа действует лимит **N запросов за T секунд** по алгоритму скользящего окна.
Состояние хранится в Redis, проверка выполняется атомарно (Lua-скрипт).

## Запуск

```bash
docker compose up -d --build
# 5 запросов за 10 секунд (см. docker-compose.yml)
for i in 1 2 3 4 5 6; do
  curl -si -X POST localhost:8000/v1/echo \
    -H 'Authorization: Bearer my-key' -H 'Content-Type: application/json' \
    -d '{"hello":"world"}' | grep -iE '^HTTP|retry-after|x-ratelimit|^\{'
done
docker compose down
```

Локально (нужен Redis на `REDIS_URL`): `uv sync && uv run uvicorn app.asgi:app`.

## Ответы

| Статус | Когда | Заголовки |
|---|---|---|
| 200 | в пределах лимита, тело эхом | `X-RateLimit-Limit`, `X-RateLimit-Remaining` |
| 429 | лимит превышен | то же + `Retry-After` (целые секунды, >= 1) |
| 401 | нет/неверный `Authorization: Bearer <key>` | `WWW-Authenticate: Bearer` |
| 503 | Redis недоступен | - |

Аутентификация выполняется до проверки лимита, поэтому 401 не расходует лимит.

## Как работает алгоритм

Для каждого ключа в Redis хранится sorted set (`ratelimit:<sha256(ключ)>`): член - уникальный id запроса,
score - время запроса в мс. Lua-скрипт выполняется в Redis атомарно:

1. `ZREMRANGEBYSCORE` удаляет записи с `score <= now - T`;
2. `ZCARD` считает оставшиеся запросы в окне;
3. если их меньше N - `ZADD` добавляет текущий запрос, `PEXPIRE` ставит TTL = T, ответ "разрешено";
4. иначе берётся самая старая запись, `Retry-After = ceil((oldest + T - now) / 1000)`, минимум 1.

**Семантика границы окна.** Окно - полуинтервал `(now - T, now]`: запись с `timestamp <= now - T` считается
истёкшей и удаляется (`ZREMRANGEBYSCORE -inf now-T` включает границу). Следовательно, запрос, сделанный в момент `t0`,
учитывается ещё при `t0 + T - 1мс` (ответ 429, `Retry-After` = 1 с) и перестаёт учитываться ровно в `t0 + T`
(новый запрос разрешён). Время считается в целых миллисекундах; запросы в одну и ту же миллисекунду не склеиваются,
так как член sorted set - уникальный uuid. Покрыто в `tests/test_rate_limit.py` (`test_boundary_*`).

Окно действительно скользящее: слот освобождается ровно через T секунд после соответствующего запроса,
а не по сбросу счётчика на границе интервала. Так как read-modify-write происходит внутри одного
Lua-вызова, параллельные запросы не могут превысить лимит (см. `tests/test_concurrency.py`).
Время берётся из инъектируемых часов приложения и передаётся в скрипт аргументом - это позволяет
тестировать скольжение окна без `sleep`. В проде используется `time.time`
(при нескольких инстансах API часы должны быть синхронизированы; при необходимости время можно брать из `TIME` Redis).
Сырые ключи в Redis не хранятся - только sha256.

## Конфигурация (переменные окружения)

| Переменная | По умолчанию | Описание |
|---|---|---|
| `RATE_LIMIT_REQUESTS` | `5` | N - число запросов в окне |
| `RATE_LIMIT_WINDOW_SECONDS` | `60` | T - длина окна в секундах |
| `REDIS_URL` | `redis://localhost:6379/0` | адрес Redis |
| `API_KEYS` | обязательно | список допустимых ключей через запятую. Без него сервис не запускается: иначе клиент мог бы обходить лимит, меняя ключ в каждом запросе. В docker-compose для демо заданы `my-key,other-key` |

## Тесты

Одна команда (зависимости ставятся автоматически):

```bash
uv run pytest
```

Используются `fakeredis[lua]` (Lua выполняется через `lupa`, реальный Redis не нужен) и управляемые часы.
Покрыто: лимит не превышен, 429 + `Retry-After`, скольжение окна, граница окна (за 1 мс до T - 429, ровно в T - 200), независимость ключей, 401, конкурентные запросы.

## Структура

```
app/config.py   настройки из env

app/main.py     create_app(): аутентификация, rate limit, /v1/echo
app/asgi.py     точка входа для uvicorn
tests/          pytest
```
